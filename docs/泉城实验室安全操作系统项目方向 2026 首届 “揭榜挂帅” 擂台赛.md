## 三、总体架构和验证边界

### 3.1 任务一架构

RISC-V 路径由 QEMU 提供物理 CPU 和设备，AxVisor 负责 vCPU、虚拟中断、vPLIC、SBI 兼容和客户机调度，Linux 或 StarryOS 运行在客户机中。Linux SMP2 使用 2 个 vCPU，宿主 AxVisor QEMU 使用 --smp 4，配置中的 phys_cpu_ids 为 [0, 1]，vPLIC context 数量为 [4]。Linux 通过 virtio-blk 取得 ext4 rootfs，挂载 /proc 后进入 /sbin/init 和 /bin/sh。

实时性测量在 StarryOS 用户态和 RT-Thread shell 中分别运行 rt_probe 或 rtprobe。每个样本记录目标唤醒时间、实际唤醒时间、完成时间、jitter、调度延迟、执行时间和 missed deadline，并由脚本计算 P99、P999 和最大值。StarryOS 的 5 ms 结果属于用户态周期唤醒链路，RT-Thread 的结果属于 RTOS 周期任务链路，Zephyr 的 busy-loop 结果属于原生低开销下界，三者不直接混写成同一种延迟。

### 3.2 任务二架构

已经验证的拓扑如下。

~~~
StarryOS guest
  -> 10.0.2.2:6000
  -> Ubuntu UDP forwarder
  -> 127.0.0.1:5000
  -> RT-Thread QEMU hostfwd
  -> RT-Thread aictrl_server UDP/5000
~~~

这条路径证明了客户机用户态网络、UDP/IP 报文、应用层协议和服务端状态机。Ubuntu relay 与 QEMU user-net hostfwd 仍然是实验环境组成部分，结果不能表述为同一 AxVisor 内两个 guest 已经完成 direct guest-to-guest，也不能表述为 tap/bridge 最终网络已经完成。

### 3.3 任务三架构

模型准备链路为 YOLOv8s 权重到固定尺寸 ONNX，再到 RKNN INT8 split 模型和 NCNN 模型。RKNN 只在 RK3588 NPU 运行时或模拟器中有意义，普通 QEMU 不具备 /dev/rknpu、DMA、IOMMU 和 NPU 中断条件。因此当前任务三结果是模型和板端程序准备，不包含 StarryOS QEMU 内的 RKNN 实际推理。

### 4.2 RISC-V IPI、vPLIC 和虚拟中断排查

调试过程中沿着客户机发起 IPI、AxVisor 接收 SBI 请求、更新虚拟中断状态、进入客户机和清除 pending 的完整链路逐层定位。

已处理或明确验证的路径包括 SBI legacy SEND_IPI 和 CLEAR_IPI、guest hart mask、host SupervisorSoft、hvip.VSSIP、vPLIC pending、claim、complete、VSEIP 注入和清除。多 context VSEIP 同步时可能误清 pending 的边界也被单独检查。Linux 在 virtio-blk 识别后停止推进的问题，最终与虚拟中断、pass-through IRQ 和 rootfs 启动阶段的交互一起复核。

这部分工作形成了 book/design/axvm-riscv-sbi-ipi.md 设计记录、qemu-riscv-ipi 回归测例和相关 vCPU 修改。它把客户机没有继续启动拆成可观测的中断状态、设备中断、SBI 调用和 rootfs 阶段，后续维护者可以沿同一证据链复现。

### 4.3 调度、中断退出和等待队列改造

当前 dirty 分支的实时性改造集中在以下技术点。

- IRQ context 中不直接执行有风险的任务切换。中断处理只设置 pending，通过统一 IRQ-exit 边界完成调度。
- 新增 IrqNotify::notify_irq_background，把需要后台处理的事件与中断入口分开。
- 调整 wait queue、任务定时器和 vCPU event snapshot，覆盖 WFI 前后事件到达的竞态，避免事件已经到达但 vCPU 继续睡眠。
- 在 AArch64 host 统一 IRQ acknowledge、EOI 和 GIC CPU interface 的边界，加入已确认 IRQ 的回归测试。
- 为 AArch64 virtual timer 增加 snapshot、arm wait、prepare run 和 rearm 流程，明确 guest timer PPI 绑定。
- 为 RISC-V vCPU 增加 timer wait 和 runtime queue 支持，并把等待事件纳入 vCPU 调度观察。
- 在 AxVM 中补充动态 FDT 创建、解析、串口和设备信息处理，保证客户机获得与运行时设备一致的描述。
- 为 FIFO、Round Robin 和 CFS 调度器增加 len、is_empty、pick_stealable_task 等可观察接口和单元测试。
- 补充任务定时器、抢占、IRQ 通知和 wait queue 竞态回归，减少只能依靠整机日志判断的问题。

## 五、任务二已经完成的工程工作

### 5.1 AICtrl/IP v1 报文和状态机

协议覆盖四类消息。

~~~
CONTROL_SET
CONTROL_ACK
STATUS_GET
STATUS_REPORT
~~~

报文包含 magic、version、message type、payload length、sequence number、checksum、控制参数、状态反馈和 error code。服务端维护 last_seq、接收计数、错误计数、策略编号以及 kp、ki、kd 等控制状态。

服务端对重复序号返回 ACK，但保持第一次应用的状态。旧序号计入错误路径并返回对应错误码。协议测试覆盖正常控制、状态回读、重复序号、旧序号、错误 magic、错误 version、错误 message type、错误控制长度、错误状态长度和错误 checksum。损坏的 STATUS_GET 也会返回带错误码的 STATUS_REPORT。协议错误不会触发客户端重试。
